## 一、架构基础（P43–P44）

### 1. 架构的本质（第 9 题）

> **架构的本质是决策**，是在**权衡方向、结构、关系以及原则**各方面因素后进行的决策。

- 信息系统项目可基于项目建设的**指导思想、设计原则和建设目标**展开各类架构的设计。
- **设计原则的数量**：太多的原则会降低架构的灵活性，许多组织倾向于只界定更高级别原则，并通常将数目限制在 **4～10 项**。

### 2. 总体参考框架（第 10、11、12、42、60 题，必背）

> 信息系统体系架构**总体参考框架由四个部分组成**：**战略系统、业务系统、应用系统和信息基础设施**。这四个部分相互关联，并构成与**管理金字塔**相一致的层次。

```
        战略系统        ← 战略管理（第一层）
   业务系统   应用系统    ← 战术管理（第二层）
      信息基础设施      ← 运营管理（第三层）
```

- **框架的定义**（第 6 题）：框架是一个用于**规划、开发、实施、管理和维持**架构的**概念性结构**；框架对架构设计至关重要。

### 3. 战略系统（P43）

- **定义**：组织中与**战略制定、高层决策**有关的管理活动和计算机辅助系统。
- 在 ISA 中，战略系统由**两部分**组成：①以信息技术为基础的**高层决策支持系统**；②组织的**战略规划体系**。
- 设立战略系统的**两重含义**：①表示信息系统对组织**高层管理者**的决策支持能力；②表示组织**战略规划**对信息系统建设的影响和要求。
- 战略规划分**长期规划**（相对稳定，如调整产品结构）与**短期规划**（根据长期规划的目的制订，易随环境和运作改变，如决定新产品的类型）。

### 4. 业务系统（P43–P44）

- **定义**：组织中完成一定业务功能的各部分（**物质、能量、信息和人**）组成的系统。
- **业务过程重组（BPR）**：以**业务流程**为中心，打破组织的**职能部门分工**，对现有业务过程进行改进或重新组织，以求在**生产效率、成本、质量、交货期**等方面取得明显改善，提高组织竞争力。
- 业务系统在 ISA 中的作用：对现有业务系统、过程、活动**建模**；在战略指导下用 BPR 原理**优化重组**；对重组后的业务建模，从而确定出**相对稳定的数据**；以此为基础进行应用系统开发和信息基础设施建设。

### 5. 应用系统（P44）

- **定义**：即应用软件系统，指信息系统中的应用软件部分。
- 按功能可包含：**事务处理系统（TPS）、管理信息系统（MIS）、决策支持系统（DSS）、专家系统（ES）、办公自动化系统（OAS）、计算机辅助设计/工艺设计/制造（CAD/CAPP/CAM）、制造执行系统（MES）**。MIS 又可按业务细分：销售、采购、库存、运输、财务、人事等子系统。
- **从架构角度看，任何层次的应用系统都包含两个基本组成部分：内部功能实现部分和外部界面部分**（第 46 题常见考点）。

### 6. 信息基础设施（P44，第 50 题）

| 部分 | 组成 |
|---|---|
| **技术基础设施** | 计算机设备、网络、系统软件、支持性软件、数据交换协议等 |
| **信息资源设施** | 数据与信息本身、数据交换的形式与标准、信息处理方法等 |
| **管理基础设施** | 信息系统部门的**组织架构**、信息资源设施管理人员的**分工**、信息基础设施的**管理方法与规章制度** |

## 二、系统架构（P44–P48）

### 1. 架构定义：6 个理解角度（第 13、46 题，必背）

| 角度 | 原文要点 |
|---|---|
| ①**抽象** | 通过描述**元素、元素的外部可见属性及元素之间的关系**来反映抽象；**仅与内部具体实现有关的细节不属于架构**（强调"外部可见"） |
| ②**多结构** | 架构由**多个结构**组成；结构从功能角度描述元素之间的关系；**个别结构一般不能代表大型信息系统架构** |
| ③**可独立于文档** | **任何软件都存在架构**，但不一定有表述文档；架构可独立于描述存在；**文档已过时则不能反映架构** |
| ④**元素及行为的集合** | 静态方面关注**大粒度（宏观）总体结构**（如分层）；动态方面关注**关键行为的共同特征** |
| ⑤**基础性** | 涉及解决**关键重复问题的通用方案（复用性）**，以及影响深远（**架构敏感**）的重要决策——**一旦贯彻，更改代价昂贵** |
| ⑥**隐含决策** | 架构是架构设计师根据**关键功能和非功能性需求**（质量属性及项目相关约束）进行设计与决策的结果 |

### 2. 架构分类（P44–P45，第 14 题）

| 分类 | 子类 | 概念与优缺点 |
|---|---|---|
| **物理架构** | **集中式** | 物理资源在空间上集中配置；早期单机系统最典型。**优点**：资源集中、便于管理、利用率较高。**缺点**：维护管理越来越困难；不利于调动用户积极性主动性；资源过于集中造成系统脆弱，易使整个系统瘫痪 |
| | **分布式** | 各地计算机系统既可在网络统一管理下工作，也可脱离网络用本地资源独立运作；**分布式架构成为信息系统的主要模式**。**优点**：按需配置资源、应变能力强、扩展方便、安全性好、单节点故障不致全网停止。**缺点**：资源分散且分属各子系统，管理标准不易统一、协调困难、不利于全局规划 |
| **逻辑架构** | — | 是**功能综合体和概念性框架**；信息系统种类繁多、规模不一、功能差异大，逻辑架构也不尽相同 |
| **系统融合** | **横向融合** | 将**同一层次**的各种职能与需求融合在一起 |
| | **纵向融合** | 把某种职能和需求的**各个层次**的业务组织在一起，沟通上下级联系 |
| | **纵横融合** | 主要从**信息模型和处理模型**两个方面综合，做到信息集中共享 |

### 3. 常用架构模型（P45–P46，第 15、17 题）

| 模型 | 要点 |
|---|---|
| **单机应用模式** | 最简单的软件结构，运行在一台物理机器上的独立应用程序，可多进程/多线程；如 CAD 领域的 CATIA、Pro/Engineer、AutoCAD，图像处理的 Photoshop、CorelDRAW |
| **两层 C/S** | 实质是 **IPC 客户端/服务器**结构的应用系统体现；**前台界面＋后台数据库服务**模式最典型 |
| **三层 C/S 与 B/S** | 前台与后台之间须通过协议通信，常见方式：①基于 TCP/IP 直接在 Socket API 自研（适合小型系统）；②自定义消息机制（封装 TCP/IP 与 Socket，消息可基于 XML）；③基于 RPC；④基于 CORBA/IIOP；⑤基于 Java RMI；⑥基于 J2EE JMS；⑦基于 HTTP（HTTP 非面向对象，对象数据先平面化再传输）。**最典型的三层 C/S 应用模式是 B/S（浏览器/服务器）** |
| **多层 C/S** | 一般三层以上，实践中主要四层：**前台界面（浏览器）、Web 服务器、中间件（应用服务器）、数据库服务器**；中间件层作用：提高可伸缩性、增加并发性能；完成请求转发与应用逻辑处理（可作请求代理/应用服务器）；增加数据安全性 |
| **MVC** | J2EE 中 View 表示层指**浏览器层**；Controller 控制器指 **Web 服务器层**；Model 模型层指**应用逻辑实现及数据持久化**部分；要求**视图与模型代码分开**；按"模型"是否将业务逻辑分离成单独服务，MVC 可分为**三层或四层**体系 |
| **SOA 面向服务架构** | 实践中借助中间件（消息中间件、交易中间件）实现，可细分为**异构系统集成、同构系统聚合、联邦体系结构**；Web 服务间开放服务用 **SOAP 与 WSDL**；**本质是消息机制或远程过程调用（RPC）** |
| **组织级数据交换总线** | 实质是一个称为**连接器**的软件系统，可基于中间件或 CORBA/IIOP 构建，功能是按预定义配置或消息头进行数据/请求/回复的接收与分发；理论上可兼顾实时交易与大数据量传输，**实践中成熟的总线主要为实时交易设计**，大数据量传输往往需单独设计 |

### 4. 规划与设计：集成架构演进（P46–P47）

以工业企业为例：**以应用功能为主线架构 → 以平台能力为主线架构 → 以互联网为主线架构**。

### 5. TOGAF 架构开发方法（P47–P48，第 18 题）

**（1）TOGAF 基础**

- TOGAF 是一种**开放式企业架构框架标准**，为标准、方法论和企业架构专业人员之间的沟通提供**一致性保障**。
- **四个目标**：①确保从关键利益相关方到团队成员都使用**相同语言**；②避免被"**锁定**"到企业架构的专有解决方案（企业内部使用而非商业目的时**免费**）；③节省时间和金钱，更有效利用资源；④实现可观的**投资回报（ROI）**。
- **TOGAF 9 的六个组件**：①**架构开发方法（ADM）**——核心；②**ADM 指南和技术**；③**架构内容框架**（架构工件结构化元模型、可重用架构构建块 ABB、典型交付成果）；④**企业连续体和工具**（分类法与工具，用于分类存储架构活动输出）；⑤**TOGAF 参考模型**（**技术参考模型 TRM** 与**集成信息基础设施参考模型 III-RM**）；⑥**架构能力框架**（组织、流程、技能、角色和职责）。

**（2）ADM 方法（核心）**

| 阶段 | 主要活动 |
|---|---|
| **准备阶段** | 为实施成功的企业架构项目做好准备：定义组织机构、特定架构框架、架构原则和工具 |
| **需求管理** | 完成需求的识别、保管和交付；按优先级顺序对各 ADM 阶段的需求进行处理；**每个阶段都建立在业务需求之上并需确认** |
| **阶段 A：架构愿景** | 设置范围、约束和期望；创建架构愿景：**定义利益相关者、确认业务上下文环境、创建架构工作说明书、取得上级批准** |
| **阶段 B：业务架构**<br>**阶段 C：信息系统架构（应用和数据）**<br>**阶段 D：技术架构** | 从业务、信息系统和技术三个层面进行架构开发；每层面完成：开发**基线架构描述**、开发**目标架构描述**、执行**差距分析**（制造/购买/重用、外包、商用、开源）、评估优先顺序、识别相依性 |
| **阶段 E：机会和解决方案** | 进行初步实施规划，确认前面阶段确定的各种构建块的交付物形式，确定主要实施项目，对项目分组并纳入过渡架构，决定途径 |
| **阶段 F：迁移规划** | 对阶段 E 确定的项目进行**绩效分析和风险评估**，制订详细的实施和迁移计划 |
| **阶段 G：实施治理** | 定义实施项目的**架构限制**，提供架构监督，发布架构合同，监测实施项目以确保符合架构要求 |
| **阶段 H：架构变更治理** | 提供**持续监测和变更管理**流程，确保架构可响应企业需求并将架构对业务的价值最大化 |

### 6. 价值驱动的体系结构（P48，第 16、19 题）

**价值模型的三个核心特征**：

| 特征 | 含义 |
|---|---|
| **价值期望值** | 对某一特定功能的需求，包括**内容（功能）、满意度（质量）和不同级别质量的实用性** |
| **反作用力** | 系统部署实际环境中，**实现某种价值期望值的难度**；通常期望越高难度越大 |
| **变革催化剂** | 环境中**导致价值期望值发生变化的某种事件**，或导致不同结果的**限制因素** |

- **反作用力和变革催化剂合称"限制因素"**；**三者统称"价值驱动因素"**。
- **结构挑战**：最早的体系结构决策产生最大价值才有意义；建议对**重要性、程度、后果和隔离**进行权衡；影响越广，重要性越高。

## 三、应用架构（P48–P49）

### 1. 五条基本原则（第 2、20 题，必背）

| 原则 | 说明 |
|---|---|
| **业务适配性原则** | 为业务变化服务，提升业务能力、支撑组织战略；具备灵活性、可扩展性，适配未来业务 |
| **应用聚合化原则** | 整合**部门级应用**，解决系统多、功能分散重叠、界限不清问题，建设**组织级应用系统** |
| **功能专业化原则** | 按**业务功能聚合规划**，建设对应应用系统，满足不同业务条线需求，实现专业化发展 |
| **风险最小化原则** | 降低系统耦合度、提升独立性，**松耦合架构**，规避单点风险，保障系统安全稳定 |
| **资产复用化原则** | 提炼重用**架构资产**，快速开发、降本增效；建设**共享基础服务**，标准化复用，适配差异化业务需求 |

### 2. 分层与分组（第 45、49、65 题）

| 动作 | 目的（原文） |
|---|---|
| **分层** | 实现**业务与技术分离**；降低各层级之间的**耦合性**；提高各层**灵活性**；有利于**故障隔离**；实现架构**松耦合**；体现以客户为中心的系统服务和交互模式，提供面向客户服务的应用架构视图 |
| **分组** | 体现**业务功能的分类和聚合**；把紧密关联的应用或功能**内聚为一个组**；指导应用系统建设，实现**系统内高内聚、系统间低耦合**；**减少重复建设** |

> **考点**：分层的目的**不包括**"实现系统内高内聚"（那是分组的目的）——这是第 45、49 题的标准陷阱。

## 四、数据架构（P49）

### 1. 定义（第 3、61 题）

> 数据架构描述了组织的**逻辑和物理数据资产**以及相关**数据管理资源**的结构。主要内容涉及**数据全生命周期**之下的架构规划，包括数据的**产生、流转、整合、应用、归档和消亡**。

合理的数据架构设计应解决：**功能定位合理性**、面向未来发展的**可扩展性**、处理效率高效（高性价比）、**数据合理分布与数据一致性**。

### 2. 五条基本原则（必背）

| 原则 | 说明 |
|---|---|
| **数据分层原则** | 解决数据**层次定位合理性**问题；约束各层建设目标、设计方法、模型、存储及对外服务规则 |
| **数据处理效率原则** | 追求**效率与成本合理化**；真正影响效率的是**大规模原始数据的存储与处理** |
| **数据一致性原则** | 减少数据**重复加工、冗余存储**，避免因架构不合理导致数据不一致，支撑数据管控体系 |
| **数据架构可扩展性原则** | 依托清晰分层定位、合理模型与存储策略；兼顾存储模型与存储技术，适配新增业务、数据整合与应用需求 |
| **服务于业务原则** | 数据架构**最终目标是服务业务**；特殊场景下可优先满足业务体验，适当放宽其他原则 |

## 五、技术架构（P49）

### 五条基本原则（第 22、53、59 题）

| 原则 | 说明 |
|---|---|
| **成熟度控制原则** | 优先选用**成熟度高、处于活跃周期**的技术；选用新型技术需持续跟踪成熟度、安全漏洞与结构性风险 |

| **人才技能覆盖原则** | 应用架构设计要匹配组织及合作方**人才的技术驾驭能力**，保障技术最佳落地 |
| **创新驱动原则** | 挖掘技术创新价值，选取可促进/引领组织发展的**核心技术**作为架构关键纽带，完善配套技术 |

## 六、网络架构（P50–P54）

### 1. 五条基本原则（第 22 题延伸）

**高可靠性、高安全性、高性能、可管理性、平台化和架构化**。

- 高安全性：通过**身份鉴别、访问控制、入侵检测**为上层应用提供保障。

### 2. 局域网架构（第 23、24、25 题）

**局域网定义与特点**：

- 为**单一组织所拥有的专用计算机网络**；
- 覆盖地理范围小，通常限定在相对独立范围内（如一座建筑或集中建筑群，**通常在 2.5 km² 内**）；
- 数据传输速率高（一般 **10 Mb/s 以上**，典型 1 Gb/s，甚至 10 Gb/s）；
- **低误码率，可靠性高**；
- 支持多种传输介质，**支持实时应用**；拓扑有**总线、环形、星形、树状**；介质分**有线/无线**；
- 通常由计算机、交换机、路由器等设备组成。

**四种局域网架构**：

| 架构 | 关键特征 | 优缺点 |
|---|---|---|
| **单核心** | 一台核心二层或三层交换设备充当核心，经若干接入交换设备连用户；三层以上可划 VLAN（VLAN 内二层转发、VLAN 间三层路由）；接入设备用二层交换机；核心与接入间可用 100M/GE/10GE | 优：结构简单、节省投资。缺：地理范围受限、要求分部紧凑；**核心设备单点故障**；扩展能力有限 |
| **双核心** | 核心采用三层及以上交换机，两台核心互联实现**网关保护或负载均衡** | 优：分部接入方便、可靠性高。缺：投资较高；对核心端口密度要求高 |
| **环形** | 多台核心交换设备连成**双 RPR 动态弹性分组环**；**MAC 层 50 ms 自愈**；两根反向光纤、双向可用、空间重用 | 优：自愈保护、节省光纤、多等级 QoS。缺：投资高；核心路由冗余设计难度高、**易形成环路**；多环间只能业务接口互通 |
| **层次（多层）** | 由**核心层、汇聚层、接入层**交换设备及用户设备组成；经边界路由接入广域网 | 优：**拓扑易于扩展**、故障可分级排查便于维护 |

### 3. 广域网架构（第 26 题）

- **定义**：将分布于比局域网更广区域的计算机设备连接起来的网络；由**通信子网与资源子网**组成。
- **多级网络**：通常由**骨干网、分布网、接入网**组成；规模较小时可仅由**骨干网和接入网**组成。

| 架构 | 关键特征 |
|---|---|
| **单核心** | 一台核心路由设备＋各局域网；结构简单、省投资；**核心单点故障导致整网失效**；扩展欠佳 |
| **双核心** | 两台核心路由设备，互连实现**网关保护或负载均衡**；多路径、**路由层面热切换**；投资高、易形成路由环路 |
| **环形** | 三台以上核心路由器构成路由环路；具备**环路控制功能**；多路径、**无缝热切换**；投资最高、占用端口多 |
| **半冗余** | 多台核心路由设备，任意核心至少存在**两条以上**连接其他路由设备的链路；**若任意两台之间均存在链路，则为全冗余（特例）**；结构灵活扩展方便，适合部署 **OSPF** 等链路状态协议；网络零散、不便管理排障 |
| **对等子域** | 路由设备划分为**两个独立子域**，子域内半冗余互连，子域间一条或多条链路互连；**子域间链路带宽应高于子域内**；适合可明显划分为两个区域且区域内部访问独立的场景 |
| **层次子域** | 划分为**多个独立子域**，子域间存在**层次关系**（高层次连接多个低层次）；**低层次子域间互访需经高层次子域完成**；扩展性好；域间路由冗余设计难度高、易形成环路或非法路由 |

### 4. 移动通信网架构（P53–P54，第 44、62 题）

- 5G 常用业务应用方式：**5GS 与 DN（数据网络）互联**、**5G 网络边缘计算**（为垂直行业提供时间敏感、高带宽业务就近分流）。
- 从 UE 通过 5GS 接入 DN 的方式存在**两种模式：透明模式和非透明模式**。
- 5G 更注重 **QoE**（服务体验）；边缘计算是提升 QoE 的重要举措。
- **SSC 三种会话连续性模式**：

| 模式 | 含义 |
|---|---|
| **SSC 模式 1** | 用户移动过程中，用户会话的 **IP 接入点始终保持不变** |
| **SSC 模式 2** | 用户移动过程中网络触发**现有会话释放并立即触发新会话建立** |
| **SSC 模式 3** | 用户移动过程中**在释放现有会话之前先建立新会话**（先建后拆） |

## 七、安全架构（P54–P59，本章分值最高）

### 1. 六类安全威胁（P54，第 32、55、57 题）

| 威胁 | 指向 |
|---|---|
| **物理安全威胁** | 对系统所用设备的威胁：自然灾害、电源故障、操作系统引导失败或数据库信息丢失、设备被盗/被毁造成数据丢失或信息泄露 |
| **通信链路安全威胁** | **在传输线路上安装窃听装置**或对通信链路进行干扰 |
| **网络安全威胁** | 因互联网开放性、国际化，容易通过技术手段窃取互联网信息 |
| **操作系统安全威胁** | 对系统平台中的软件或硬件芯片植入威胁，如"**木马**"和"**陷阱门**"、BIOS 万能密码 |
| **应用系统安全威胁** | 对网络服务或用户业务系统安全的威胁，也受"木马"和"陷阱门"威胁 |
| **管理系统安全威胁** | 人员管理疏忽引发人为漏洞，如人为拷贝、拍照、抄录盗取信息 |

> **注意**：第 27 题题干"对于网络服务或用户业务系统安全的威胁，也受到木马和陷阱门的威胁"→ **应用系统安全威胁**（不是网络安全）。

### 2. 常见安全威胁（P54–P55，18 种，选择题干扰项来源）

信息泄露、破坏信息的完整性、拒绝服务、非法访问、窃听、业务流分析、假冒、旁路控制、授权侵犯（内部攻击）、特洛伊木马、陷阱门、抵赖、重放、计算机病毒、人员渎职、媒体废弃、物理侵入、窃取、业务欺骗。

### 3. 定义和范围：三道安全防线（P55）

| 防线 | 目标/任务 |
|---|---|
| **系统安全架构** | 目标是如何在**不依赖外部防御系统**的情况下，**从源头打造自身的安全** |
| **安全技术体系架构** | 任务是构建**通用的安全技术基础设施**（安全基础设施、安全工具和技术、安全组件与支持系统），系统性增强各部分防御能力 |
| **审计架构** | 审计的范围主要包括**安全风险在内的所有风险** |

### 4. 整体架构设计（P55）

- 构建信息安全保障体系框架应包括**技术体系、组织机构体系和管理体系**三部分。
- 换言之，**人、管理和技术手段**是信息安全架构设计的**三大要素**；构建**动态**的信息与网络安全保障体系框架是实现系统安全的保障。

### 5. WPDRRC 模型（P55–P56，第 4、28、30、31 题，必背）

> 我国信息安全专家组提出的信息系统安全保障体系建设模型；在 **PDRR（防护/检测/响应/恢复）**模型基础上**前后增加了预警和反击功能**。**WPDRRC 有六个环节和三大要素。**

**六个环节**：

| 环节 | 主要内容 |
|---|---|
| **预警（W）** | 利用远程安全评估系统提供的**模拟攻击技术**，检查系统可能存在的被利用薄弱环节，收集和测试安全风险所在，以直观方式报告并提供解决方案建议 |
| **保护（P）** | 采用成熟的信息安全技术及方法实现网络与信息的保护；主要内容：**加密机制、数字签名机制、访问控制机制、认证机制、信息隐藏和防火墙技术**等 |
| **检测（D）** | 通过检测和监控网络与系统发现新威胁和弱点、强制执行安全策略；主要内容：**入侵检测、系统脆弱性检测、数据完整性检测和攻击性检测**等；形成动态检测制度、奖励报告协调机制，提高检测实时性 |
| **响应（R）** | 主要内容：**应急策略、应急机制、应急手段、入侵过程分析和安全状态评估**等；处理包括**封堵、隔离、报告**等能力 |
| **恢复（R）** | 主要内容：**容错、冗余、备份、替换、修复和恢复**等 |
| **反击（C）** | 采用高新技术手段**侦察、提取计算机犯罪分子的作案线索与犯罪证据**，形成强有力的取证能力和依法打击手段 |

**三大要素**：**人员是核心；策略是桥梁；技术是保证。**

> **考点**：第 31 题"入侵过程分析和安全状态评估"→ **响应**环节；第 30 题"策略"→ **桥梁**。

### 6. 架构设计：安全保障体系五个层面（P56）

| 层面 | 主要内容 |
|---|---|
| **物理安全** | 环境安全、设备安全、媒体安全 |
| **系统安全** | 是系统整体安全的**基础**；网络结构安全、操作系统安全、应用系统安全 |
| **网络安全** | 是整个安全解决方案的**关键**；访问控制、通信保密、入侵检测、网络安全扫描、防病毒 |
| **应用安全** | **资源共享**和**信息存储**两个方面 |
| **安全管理** | 三方面：制定健全的安全管理体制、构建安全管理平台、增强人员安全防范意识 |

- **系统安全保障体系**由**安全服务、协议层次和系统单元**三个层面组成，且每层都涵盖安全管理的内容；设计主要考虑：安全区域策略的确定、统一配置和管理防病毒系统、网络与信息安全管理。

### 7. 设计要点（P56–P57，第 32、57 题）

- **系统安全设计**：网络结构安全（拓扑合理、线路冗余、路由冗余、防单点失败）；操作系统安全（采用安全性较高系统并安全配置、关闭不常用有隐患应用、权限限制/加强口令；配备安全扫描系统发现漏洞及时升级）；应用系统安全（应用服务器尽量不开放不常用协议端口，关闭 HTTP、FTP、Telnet 等服务，加强登录身份认证）。
- **网络安全设计**：隔离与访问控制要有严格管制制度；**防火墙是网络安全中最基本、最经济、最有效的措施**；入侵检测系统一般包括**控制台和探测器（网络引擎）**；**反病毒技术包括预防病毒、检测病毒和杀毒三种**。
- **应用安全设计**：资源共享要严格控制内部员工对共享资源的使用；信息存储要对数据库做安全备份。
- **安全管理设计**：健全体制、构建平台、培训员工安全意识。

### 8. OSI 安全架构（P57，第 8、33、35、56 题，必背）

> OSI 定义了 7 层协议，其中**除第 5 层（会话层）外，每一层均能提供相应的安全服务**。实际上最适合配置安全服务的是**物理层、网络层、传输层及应用层**，其他层都不宜配置安全服务。

- **5 类安全服务**：**鉴别、访问控制、数据机密性、数据完整性和抗抵赖性**。
- OSI 定义的**分层多点安全技术体系架构**又称**深度防御安全技术体系架构**，通过三种方式将防御能力分布至整个信息系统：

| 方式 | 内容 |
|---|---|
| **多点技术防御** | **网络和基础设施**（确保可用性，抵御拒绝服务等攻击）；**边界**（抵御主动网络攻击，流量过滤和控制、入侵检测）；**计算环境**（抵御内部、近距离分布攻击，主机和工作站提供足够访问控制） |
| **分层技术防御** | 每种机制应代表**一种唯一的障碍**，同时包括**保护和检测**方法；**在外部和内部边界同时使用嵌套的防火墙并配合入侵检测就是分层技术防御的实例** |
| **基础设施支撑性** | **公钥基础设施（PKI）**：通用联合处理方式，安全创建、分发和管理公钥证书与传统对称密钥；**检测和响应基础设施**：迅速检测并响应入侵行为 |

### 9. 认证（鉴别）框架（P57）

- 鉴别有两个重要关系背景：①**实体由申请者代表**，申请者与验证者之间存在特定通信关系（如实体鉴别）；②**实体为验证者提供数据项来源**。
- **鉴别方式 5 种**：①**已知的**（秘密口令）；②**拥有的**（IC 卡、令牌）；③**不改变的特性**（生物特征）；④**相信可靠的第三方建立的鉴别**（递推）；⑤**环境**（如主机地址）。
- **鉴别信息 3 类**：交换鉴别信息、申请鉴别信息、验证鉴别信息。
- **鉴别服务 9 个阶段**：安装、修改鉴别信息、分发、获取、传送、验证、停活、重新激活、取消安装。

### 10. 访问控制框架（P58）

| 缩写 | 含义 |
|---|---|
| **ACI** | 访问控制信息：用于访问控制目的的任何信息，**包括上下文信息** |
| **ADI** | 访问控制判决信息：作出特定访问控制判决时可供 **ADF** 使用的部分（或全部）ACI |
| **ADF** | 访问控制判决功能：通过对访问请求、ADI 及上下文**使用访问控制策略规则**作出判决 |
| **AEF** | 访问控制实施功能：确保**只有对目标允许的访问**才由发起者执行 |

- 涉及访问控制的角色：**发起者、AEF、ADF、目标**。
- **三种 ADI**：发起者 ADI（由绑定到发起者的 ACI 导出）、目标 ADI、访问请求 ADI。
- ADF 的其他输入：访问控制策略规则、必要**上下文信息**（发起者位置、访问时间、特殊通信路径）。

### 11. 机密性、完整性、抗抵赖框架（P58–P59，第 47 题）

- **机密性框架**：目的是确保信息**仅对被授权者可用**。保证方式：①**禁止访问**（访问控制、物理媒体保护、路由选择控制）；②**隐藏数据语义**；③**分散数据**（如跳频）。通过**加密**提供机密性（对称与非对称）。
- **完整性框架**：目的是通过**阻止威胁或探测威胁**，保护数据完整性及相关属性完整性。所谓完整性，就是**数据不以未经授权方式改变或损毁**的特征。
  - 按**防范的违规**分类：**未授权的数据修改、未授权的数据创建、未授权的数据删除、未授权的数据插入、未授权的数据重放**（5 类）。
  - 按**保护方法**分类：阻止完整性损坏、检测完整性损坏。
  - 按**是否支持恢复机制**分类：有恢复机制、无恢复机制。
- **抗抵赖性框架**：服务包括证据的**生成、验证和记录**，以及解决纠纷时的证据恢复和再次验证。**抗抵赖由 4 个独立阶段组成**：①**证据生成**；②**证据传输、存储及恢复**；③**证据验证**；④**解决纠纷**。

### 12. 数据库系统安全设计（P59，第 38、39 题）

- 从 DBMS 角度，解决运行安全与信息安全的安全策略一般为：**用户管理、存取控制、数据加密、审计跟踪和攻击检测**。
- **数据库完整性**是指数据库中数据的**正确性和相容性**；针对数据库系统安全需**重点关注完整性设计**。
- **完整性设计 7 条基本原则**：
  1. 根据约束类型确定实现的**系统层次和方式**，提前考虑对**性能**的影响；**静态约束尽量包含在数据库模式中，动态约束由应用程序实现**；
  2. **实体完整性约束和引用完整性约束**是关系数据库最重要的完整性约束，在不影响系统关键性能前提下尽量应用；
  3. **慎用触发器**：性能开销大、多级触发难控制易出错；非用不可时最好使用 **Before 型语句级触发器**；
  4. 需求分析阶段就制定**完整性约束的命名规范**（有意义英文单词、缩写、表名列名及下划线组合）；
  5. 根据业务规则对完整性进行**细致测试**，尽早排除约束间冲突和对性能的影响；
  6. 要有**专职的数据库设计小组**，自始至终负责分析、设计、测试、实施及早期维护；
  7. 应采用合适的 **CASE 工具**降低各阶段工作量。
- **完整性约束 6 类**：列级静态、元组级静态、关系级静态、列级动态、元组级动态、关系级动态；**动态约束通常由应用软件实现**。
- **完整性设计 3 个阶段**：**需求分析阶段、概念结构设计阶段、逻辑结构设计阶段**。

## 八、云原生架构（P60–P62，第 5、7、40、43、52、54、64 题）

### 1. 定义（第 5 题基础）

> 从技术角度，云原生架构是**基于云原生技术的一组架构原则和设计模式的集合**，旨在将云应用中的**非业务代码部分最大化剥离**，让**云设施接管应用原有的非功能特性**（弹性、韧性、安全、可观测性、灰度等），使业务不再受非功能性业务中断困扰，同时具备**轻量、敏捷、高度自动化**的特点。技术部分依赖传统云计算三层概念：**IaaS、PaaS、SaaS**。

- **云原生的代码三部分**（第 40 题）：①**业务代码**（实现业务逻辑）；②**三方软件**（业务代码依赖的所有三方库，包括业务库和基础库）；③**处理非功能特性的代码**（实现高可用、安全、可观测性等非功能能力）。**三部分中只有业务代码是核心**，另两部分是附属物。
- **非功能性特性大量委托**：任何应用都提供功能性特性（真正带来价值，如建客户资料、处理订单、支付、组织管理、业务字典、搜索）与非功能性特性（无直接业务价值但必不可少：高可用、容灾、安全、可运维性、易用性、可测试性、灰度发布）。

### 2. 七条基本原则（第 5 题，必背）

| 原则 | 说明 |
|---|---|
| **服务化原则** | 分布式环境下的**限流降级、熔断隔仓、灰度、反压、零信任安全**等，本质上都是基于**服务流量**（而非网络流量）的控制策略；服务化还在于从架构层面抽象业务模块关系、标准化服务流量传输 |
| **弹性原则** | 系统部署规模可随业务量**自动伸缩**，无须按事先容量规划准备固定硬件和软件资源（第 52 题"备电 3 分钟恢复"属此） |
| **可观测原则** | 通过**日志、链路跟踪和度量**等手段，使一次点击背后多次服务调用的耗时、返回值和参数清晰可见，可下钻到三方软件调用、SQL 请求、节点拓扑、网络响应；获得关联分析能力 |
| **韧性原则** | 韧性代表**当软件所依赖的软硬件组件出现各种异常时，软件表现出来的抵御能力**；核心目标是提升**平均无故障时间（MTBF）**；包括服务异步化、重试/限流/降级/熔断/反压、主从、集群、AZ 内高可用、单元化、跨区域容灾、异地多活容灾 |
| **所有过程自动化原则** | 通过 **IaC、GitOps、OAM、Kubernetes Operator** 和自动化交付工具在 **CI/CD 流水线**中实践，标准化软件交付过程，实现整个交付和运维的自动化 |
| **零信任原则** | 默认**不应信任网络内部和外部的任何人/设备/系统**；基于认证和授权重构访问控制的信任基础（IP 地址、主机、地理位置、所处网络均不能作为可信凭证）；第一个核心问题是**身份** |
| **架构持续演进原则** | 云原生架构本身必须具备**持续演进能力**，不是封闭式架构；还需考虑组织（如架构控制委员会）层面的架构治理和风险控制 |

### 3. 七种常用架构模式（第 7、41、64 题）

| 模式 | 要点 |
|---|---|
| **服务化架构模式** | 典型模式是**微服务**和**小服务**；小服务是一组关系非常密切、**共享数据**的服务的组合，适合**非常大型**的软件系统，避免接口颗粒度过细导致过多调用损耗和治理复杂度；把**代码模块关系与部署关系分离**，每接口可部署不同实例数、单独扩缩容、单独升级 |
| **Mesh 化架构模式** | 把中间件框架（RPC、缓存、异步消息等）**从业务进程中分离**，让中间件 SDK 与业务代码**进一步解耦**，中间件升级对业务进程无影响；大量分布式架构模式（熔断、限流、降级、重试、反压、隔仓）由 **Mesh 进程**完成；获得更好安全性（零信任）、按流量动态环境隔离、基于流量做冒烟/回归测试 |
| **Serverless 模式** | 将"**部署**"这个动作从运维中"收走"，开发者不用关心运行地点、操作系统、网络配置、CPU 性能；**不适合**有状态应用（调度不做状态同步，可能上下文丢失）、长时间后台运行的密集型计算、频繁外部 I/O；**非常适合事件驱动的数据计算任务、计算时间短的请求/响应应用、没有复杂相互调用的长周期任务**（第 64 题） |
| **存储计算分离模式** | **CAP 困难主要针对有状态应用**，无状态应用不存在 C 维度，可获得很好的 A 和 P，从而获得更好弹性；推荐把各类暂态数据（session）、结构化和非结构化持久数据都用云服务保存；对性能敏感的场景可用**时间日志＋快照（检查点）**实现重启后快速增量恢复 |
| **分布式事务模式** | 见下表 |
| **可观测架构** | 包括 **Logging、Tracing、Metrics** 三方面：Logging 提供多级别详细信息跟踪（**由应用开发者主动提供**）；Tracing 提供一个请求从前端到后端的**完整调用链路跟踪**（分布式场景尤其有用）；Metrics 提供系统量化的多维度度量。建立可观测性的主要目标是**度量 SLO 以优化 SLA**，需为各组件定义清晰 SLO（并发度、耗时、可用时长、容量） |
| **事件驱动架构（EDA）** | 本质是一种**应用/组件间的集成架构模式**；不仅用于（微）服务解耦，还应用于：增强服务韧性、**CQRS（命令查询的责任分离）**、数据变化通知、构建开放式接口、事件流处理、基于事件触发的响应 |

**五种分布式事务模式对比（第 41 题）**：

| 模式 | 特点 |
|---|---|
| **XA** | 具备**很强的一致性**，但**性能差** |
| **基于消息的最终一致性** | **性能很高**，但**通用性有限** |
| **TCC** | 完全由应用层控制事务，**隔离性可控**、较高效；但**对业务侵入性非常强**，设计开发维护成本高 |
| **SAGA** | 与 TCC 优缺点类似，但**没有 Try 阶段**，每个正向事务对应一个**补偿事务**，开发维护成本高 |
| **SEATA 的 AT 模式** | **性能非常高**，**无代码开发工作量**，可自动执行回滚；存在**使用场景限制** |

## 九、五表原则总汇（P63，考试高频，必背）

| 架构 | 原则（数量） |
|---|---|
| **应用架构** | 业务适配性、应用聚合化、功能专业化、风险最小化、资产复用化（**5**） |
| **数据架构** | 数据分层、数据处理效率、数据一致性、数据架构可扩展性、服务于业务（**5**） |
| **技术架构** | 成熟度控制、技术一致性、局部可替换、人才技能覆盖、创新驱动（**5**） |
| **网络架构** | 高可靠性、高安全性、高性能、可管理性、平台化和架构化（**5**） |
| **云原生架构** | 服务化、弹性、可观测、韧性、所有过程自动化、零信任、架构持续演进（**7**） |

> **27 条原则的快速归属法**：
> - 看到"**业务/聚合/专业化/复用/风险**"→ 应用架构；
> - 看到"**分层/效率/一致性/扩展/服务业务**"→ 数据架构；
> - 看到"**成熟度/异构/可替换/人才/创新**"→ 技术架构；
> - 看到"**可靠/安全/性能/可管理/平台化**"→ 网络架构；
> - 看到"**服务化/弹性/可观测/韧性/自动化/零信任/演进**"→ 云原生。

## 十、高频对比表

### 对比 1：集中式 vs 分布式

| 维度 | 集中式 | 分布式 |
|---|---|---|
| 资源配置 | 空间集中 | 按需分散配置 |
| 管理 | 便于管理、利用率高 | 标准不易统一、协调困难 |
| 可靠性 | 脆弱、易整体瘫痪 | 单节点故障不影响整体 |
| 地位 | 早期单机系统典型 | **信息系统主要模式** |

### 对比 2：三类架构

| 架构 | 定义关键词 |
|---|---|
| 物理架构 | 拓扑关系（集中式/分布式） |
| 逻辑架构 | 功能综合体和概念性框架 |
| 系统融合 | 横向/纵向/纵横融合 |

### 对比 3：局域网四架构

| 架构 | 一句话 |
|---|---|
| 单核心 | 结构简单但单点故障 |
| 双核心 | 网关保护/负载均衡，投资高 |
| 环形 | RPR 50 ms 自愈，易成环 |
| 层次 | 核心-汇聚-接入，易扩展、分级排障 |

### 对比 4：广域网六架构

| 架构 | 核心特征 |
|---|---|
| 单核心 | 单点故障致整网失效 |
| 双核心 | 热切换、多路径 |
| 环形 | 环路控制、无缝热切换 |
| 半冗余 | 任意核心≥2 条链路；全冗余为特例；适合 OSPF |
| 对等子域 | 两个子域、域间带宽更高 |
| 层次子域 | 多子域、低层互访走高层次 |

### 对比 5：PDRR vs WPDRRC

| 模型 | 环节 |
|---|---|
| PDRR | 防护、检测、响应、恢复（4） |
| P2DR | 安全策略、防护、检测、响应（4） |
| **WPDRRC** | **预警、保护、检测、响应、恢复、反击（6）＋人员/策略/技术（3 要素）** |

### 对比 6：三道防线

| 防线 | 关键词 |
|---|---|
| 系统安全架构 | 不依赖外部、**从源头**打造自身安全 |
| 安全技术体系架构 | 构建通用安全技术基础设施，系统性增强 |
| 审计架构 | 涵盖包括安全风险在内的**所有风险** |

### 对比 7：深度防御三方式

| 方式 | 关键词 |
|---|---|
| 多点技术防御 | 网络与基础设施/边界/计算环境，**位置分布** |
| 分层技术防御 | 每种机制是唯一障碍、**保护＋检测**；嵌套防火墙＋IDS 为实例 |
| 基础设施支撑性 | PKI＋检测响应基础设施 |

### 对比 8：垂直 vs 水平（防混淆）

- **纵向融合**＝把同一职能的各层业务组织在一起（沟通上下级）。
- **横向融合**＝同一层次的各种职能与需求融合。

## 十一、陷阱清单（25 条，逐条自测）

1. 架构本质是**决策**，不是"设计"；原则数量通常限制在 **4～10 项**。
2. 总体参考框架四部分：战略系统、业务系统、应用系统、**信息基础设施**（不是"技术系统"）。
3. 信息基础设施三分：技术、**信息资源**、管理（不是"网络设施"）。
4. 战略系统由"高层决策支持系统＋战略规划体系"两部分组成。
5. 应用系统从架构看只含两部分：**内部功能实现部分＋外部界面部分**。
6. 架构定义强调元素的"**外部可见**"属性；内部实现细节不属于架构。
7. "任何软件都存在架构，但不一定有文档"——文档过时则不能反映架构。
8. 物理架构分集中式与分布式；**分布式是主要模式**。
9. 逻辑架构是"**功能综合体和概念性框架**"。
10. 系统融合三型：横向、纵向、**纵横**。
11. 三层 C/S 最典型应用模式是 **B/S**。
12. **SOA 的本质是消息机制或远程过程调用（RPC）**。
13. MVC 中 Controller 在 **Web 服务器层**；View 在浏览器层；Model 含应用逻辑与数据持久化。
14. TOGAF 六组件核心是 **ADM**；参考模型是 **TRM 与 III-RM**。
15. ADM 阶段顺序：准备→需求管理→A 愿景→B 业务→C 信息系统（应用+数据）→D 技术→E 机会与解决方案→F 迁移规划→G 实施治理→H 架构变更治理。
16. 价值模型三核心：价值期望值、反作用力、**变革催化剂**；后两者为"限制因素"。
17. 应用分层目的**不含**"系统内高内聚"（那是分组目的）。
18. 数据架构五原则里最容易漏的是"**服务于业务原则**"。
19. 技术架构"局部可替换原则"关注**技术生命周期与退役影响**，不是"局部代码可替换"。
20. 局域网覆盖范围常考 **2.5 km²**，速率"**10 Mb/s 以上，典型 1 Gb/s**"。
21. 局域网四架构中"易形成环路"的是**环形**；"单点故障"的是**单核心**。
22. 广域网"半冗余"的定义：任意核心路由设备至少存在**两条以上**连接其他路由设备的链路；全冗余是特例。
23. WPDRRC 六环节顺序：**预警→保护→检测→响应→恢复→反击**；三要素：**人员核心、策略桥梁、技术保证**。
24. OSI 中**除会话层（第 5 层）外**每层都能提供安全服务；最适合配置的是**物理层、网络层、传输层、应用层**。
25. 抗抵赖 **4 阶段**：证据生成、证据传输存储及恢复、证据验证、解决纠纷。
